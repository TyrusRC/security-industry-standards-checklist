# K8S security test cases

140 tests. Tick the box when the test passes.


## AUTH

- [ ] **K8S-AUTH-001** Check that users sign in through an external identity provider  
  *Severity if fail:* High | *Type:* Config Review  
  *Objective:* Finds clusters where human users rely on built-in credentials with no revocation or audit.  
  *Steps:*
  1. List the authentication methods in use on the API server.
  2. Check that users authenticate through OIDC or the managed cloud identity service.
  3. Find static token files, basic auth files and long-lived client certificates for users.
  4. Check that the identity provider enforces MFA.
  *Example:* `kubectl -n kube-system get pod -l component=kube-apiserver -o yaml | grep -E "oidc|token-auth-file|client-ca"; kubectl config view --raw | grep -E "client-certificate|token"`  
  *Expected:* Users sign in with short-lived tokens from an external identity provider with MFA. No static token file exists and no user certificates are valid for years.  
  *Refs:* k8s_top10: K09; cloud_native_top10: CNAS-3; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-287, CWE-798; attack: T1078; nist_800_53: IA-2, IA-5

- [ ] **K8S-AUTH-002** Check that anonymous API access is off or has no rights  
  *Severity if fail:* High | *Type:* Manual  
  *Objective:* Finds API servers that serve anonymous requests with rights.  
  *Steps:*
  1. Send a request to the API without credentials.
  2. Send requests to resource paths as system:anonymous.
  3. List ClusterRoleBindings for system:anonymous and system:unauthenticated.
  4. On self-managed clusters, read the anonymous-auth flag.
  *Example:* `curl -k https://<api>:6443/api/v1/namespaces; curl -k https://<api>:6443/version; kubectl get clusterrolebindings -o json | jq ".items[] | select(.subjects[]?.name | IN(\"system:anonymous\",\"system:unauthenticated\"))"`  
  *Expected:* Requests with no credentials get HTTP 401 or 403. No role grants rights to system:anonymous or system:unauthenticated beyond the minimum.  
  *Refs:* k8s_top10: K09, K06; cloud_native_top10: CNAS-3; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-306, CWE-287; attack: T1190; nist_800_53: IA-2, AC-3

- [ ] **K8S-AUTH-003** Check that service account tokens are not used outside the cluster  
  *Severity if fail:* High | *Type:* Config Review  
  *Objective:* Finds long-lived service account tokens that people or external systems use.  
  *Steps:*
  1. Find Secrets of type service-account-token.
  2. Search the audit log for requests from service accounts with source IPs outside the cluster.
  3. Check CI and external tools for stored cluster tokens.
  4. Check the expiry of each token.
  *Example:* `kubectl get secrets -A --field-selector type=kubernetes.io/service-account-token; kubectl create token <sa> --duration 1h`  
  *Expected:* No external system uses a long-lived service account token. External tools use short-lived tokens from TokenRequest or a federated identity.  
  *Refs:* k8s_top10: K09; cloud_native_top10: CNAS-3; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-798; attack: T1528, T1550.001; nist_800_53: IA-5, IA-2

- [ ] **K8S-AUTH-004** Check use of client certificates for user access  
  *Severity if fail:* Medium | *Type:* Config Review  
  *Objective:* Finds user client certificates that cannot be revoked and last for a long time.  
  *Steps:*
  1. List user kubeconfig entries that use client certificates.
  2. Check the validity period of each certificate.
  3. Check the break-glass process for certificate use.
  4. Check that the cluster CA is not shared between environments.
  *Example:* `openssl x509 -in <client.crt> -noout -dates -subject; kubectl get csr`  
  *Expected:* User client certificates are used only for break-glass access. They are short-lived, listed, and the process to re-key the cluster is documented.  
  *Refs:* k8s_top10: K09; cloud_native_top10: CNAS-3; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-287; attack: T1078; nist_800_53: IA-5, SC-12

- [ ] **K8S-AUTH-005** Check that kubelets reject anonymous requests  
  *Severity if fail:* Critical | *Type:* Manual  
  *Objective:* Finds kubelets that accept unauthenticated calls and so allow command execution on pods.  
  *Steps:*
  1. Send a request to port 10250 of a node without credentials.
  2. Send a request to the read-only port 10255.
  3. Read the kubelet configuration for anonymous auth and authorization mode.
  4. Check that webhook authorization is on.
  *Example:* `curl -k https://<node>:10250/pods; curl http://<node>:10255/pods; grep -A3 -E "anonymous|authorization" /var/lib/kubelet/config.yaml`  
  *Expected:* The kubelet returns 401 or 403 for anonymous requests. Anonymous auth is off, authorization mode is Webhook, and port 10255 is closed.  
  *Refs:* k8s_top10: K09, K06; cloud_native_top10: CNAS-3; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-306; attack: T1609, T1613; nist_800_53: IA-2, AC-3

- [ ] **K8S-AUTH-006** Check that nodes join the cluster only with controlled credentials  
  *Severity if fail:* High | *Type:* Config Review  
  *Objective:* Finds clusters where an unknown host can join as a node and gain access to workloads.  
  *Steps:*
  1. List the bootstrap tokens and their expiry.
  2. Check the approval rules for certificate signing requests from nodes.
  3. Test a join with an expired token.
  *Example:* `kubeadm token list; kubectl get csr; kubectl -n kube-system get pod -l component=kube-apiserver -o yaml | grep authorization-mode`  
  *Expected:* Bootstrap tokens expire in a short time. Node certificate requests need approval, and unknown hosts cannot join the cluster.  
  *Refs:* k8s_top10: K09, K07; cloud_native_top10: CNAS-3; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-287, CWE-306; attack: T1078; nist_800_53: IA-3, IA-5


## CMP

- [ ] **K8S-CMP-001** Run a hardening scan on the cluster components  
  *Severity if fail:* Medium | *Type:* Automated  
  *Objective:* Finds control plane and node settings that stay on weak defaults.  
  *Steps:*
  1. Run a configuration benchmark tool against the control plane and nodes.
  2. List all failed checks with the component name.
  3. Rank the failed checks by risk for this cluster.
  4. Record accepted deviations with an owner.
  *Example:* `kube-bench run; kubescape scan; trivy k8s --report summary cluster`  
  *Expected:* Failed checks are fixed or have an accepted reason with an owner. API server, controller manager, scheduler, kubelet and etcd settings are hardened.  
  *Refs:* k8s_top10: K07; cloud_native_top10: CNAS-1; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-1188; attack: T1190; nist_800_53: CM-6, CM-2

- [ ] **K8S-CMP-002** Check that Kubernetes and its components are on a supported release  
  *Severity if fail:* High | *Type:* Config Review  
  *Objective:* Finds clusters on end-of-life versions that no longer get security fixes.  
  *Steps:*
  1. Get the version of the API server, kubelets and kube-proxy.
  2. Compare each to the list of supported releases.
  3. Check the patch level against the latest security fixes.
  4. Check the upgrade plan and the owner.
  *Example:* `kubectl version; kubectl get nodes -o custom-columns=NAME:.metadata.name,KUBELET:.status.nodeInfo.kubeletVersion,RUNTIME:.status.nodeInfo.containerRuntimeVersion`  
  *Expected:* All components run a supported release with current patches. A dated upgrade plan exists for any component that is behind.  
  *Refs:* k8s_top10: K07; cloud_native_top10: CNAS-7; cheatsheet: Kubernetes_Security_Cheat_Sheet, Docker_Security_Cheat_Sheet; cwe: CWE-1104, CWE-1395; attack: T1190, T1068; nist_800_53: SI-2, RA-5

- [ ] **K8S-CMP-003** Check patch level of the container runtime and the node kernel  
  *Severity if fail:* High | *Type:* Config Review  
  *Objective:* Finds nodes with known container escape or kernel privilege escalation flaws.  
  *Steps:*
  1. List the runtime and kernel versions on all nodes.
  2. Compare them to the current security advisories for the runtime, runc and the kernel.
  3. Check the node image age.
  4. Check the process to replace or patch nodes.
  *Example:* `kubectl get nodes -o wide; uname -r; runc --version; containerd --version; trivy rootfs / (on the node)`  
  *Expected:* Runtime, runc and kernel have no open known critical flaws. Nodes are replaced or patched on a set schedule.  
  *Refs:* k8s_top10: K07, K01; cloud_native_top10: CNAS-7; cheatsheet: Docker_Security_Cheat_Sheet, Kubernetes_Security_Cheat_Sheet; cwe: CWE-1395; attack: T1611, T1068; nist_800_53: SI-2, RA-5

- [ ] **K8S-CMP-004** Check hardening of the node operating system  
  *Severity if fail:* Medium | *Type:* Config Review  
  *Objective:* Finds general-purpose node images that carry many unneeded services and packages.  
  *Steps:*
  1. List the node operating system and image for each node pool.
  2. Check if the image is a minimal container-focused OS.
  3. List the services and packages on a sample node.
  4. Check the firewall rules and local accounts of the node.
  *Example:* `kubectl get nodes -o wide; systemctl list-units --type=service --state=running; ss -tlnp`  
  *Expected:* Nodes use a minimal OS image with few services. Firewall rules are strict, and no unneeded packages are present.  
  *Refs:* k8s_top10: K07; cloud_native_top10: CNAS-1; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-1188; attack: T1133; nist_800_53: CM-7, CM-6

- [ ] **K8S-CMP-005** Check API server flags for admission control and secure access  
  *Severity if fail:* High | *Type:* Config Review  
  *Objective:* Finds API server settings that turn off protections for requests and objects.  
  *Steps:*
  1. Read the command line of the API server.
  2. Check that the list of enabled admission plugins has no disabled security plugins.
  3. Check the TLS settings and the anonymous-auth flag.
  4. Check the audit and authorization flags.
  *Example:* `kubectl -n kube-system get pod -l component=kube-apiserver -o yaml | grep -E "enable-admission|disable-admission|anonymous-auth|tls-"; kube-bench run --targets master`  
  *Expected:* The API server has no disabled security plugins, anonymous auth is off, and the TLS settings are strong.  
  *Refs:* k8s_top10: K07, K04; cloud_native_top10: CNAS-1; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-1188, CWE-319; attack: T1190; nist_800_53: CM-6, SC-8

- [ ] **K8S-CMP-006** Build an inventory of clusters, namespaces, workloads and owners  
  *Severity if fail:* Medium | *Type:* Manual  
  *Objective:* Finds unknown, abandoned or unowned clusters, namespaces and workloads that nobody patches.  
  *Steps:*
  1. List all clusters of the organization from the cloud accounts.
  2. List namespaces and workloads in each cluster with owner labels.
  3. Find workloads with no owner or with no recent deploy.
  4. Compare the result to the asset register.
  *Example:* `aws eks list-clusters; az aks list; gcloud container clusters list; kubectl get ns --show-labels; kubectl get deploy -A -o wide`  
  *Expected:* Every cluster, namespace and workload is in the asset register with an owner. Abandoned items are removed.  
  *Refs:* k8s_top10: K07; cloud_native_top10: CNAS-8; cheatsheet: Infrastructure_as_Code_Security_Cheat_Sheet, Kubernetes_Security_Cheat_Sheet; cwe: CWE-1104; nist_800_53: CM-8


## DKR

- [ ] **K8S-DKR-001** Check that the Docker daemon socket is not exposed  
  *Severity if fail:* Critical | *Type:* Config Review  
  *Objective:* Finds hosts and containers where access to the Docker API gives root on the host.  
  *Steps:*
  1. Check if the daemon listens on a TCP port.
  2. Check the permissions and group members of /var/run/docker.sock.
  3. List containers that mount the socket, also with a read-only flag.
  4. Check if remote API access uses TLS and client certificates.
  *Example:* `ss -tlnp | grep dockerd; ls -l /var/run/docker.sock; docker ps -q | xargs docker inspect --format "{{.Name}} {{.Mounts}}" | grep docker.sock`  
  *Expected:* The daemon does not listen on unencrypted TCP. No container mounts the socket. Access to the socket is limited to named admins.  
  *Refs:* k8s_top10: K01; cloud_native_top10: CNAS-1; cheatsheet: Docker_Security_Cheat_Sheet; cwe: CWE-306, CWE-668; attack: T1610, T1611; nist_800_53: AC-3, CM-7

- [ ] **K8S-DKR-002** Check that Docker hosts use rootless mode or user namespace remapping  
  *Severity if fail:* Medium | *Type:* Config Review  
  *Objective:* Finds daemons and containers where root in the container is root on the host.  
  *Steps:*
  1. Check if the daemon runs in rootless mode.
  2. If not, read the userns-remap setting.
  3. Run id inside a container and compare it to the host user.
  4. Check the limits of rootless mode for the workload.
  *Example:* `docker info --format "{{.SecurityOptions}}"; cat /etc/docker/daemon.json; docker run --rm alpine id`  
  *Expected:* The daemon runs rootless or with user namespace remapping, and container root maps to an unprivileged host user.  
  *Refs:* k8s_top10: K01; cloud_native_top10: CNAS-1; cheatsheet: Docker_Security_Cheat_Sheet; cwe: CWE-250; attack: T1611; nist_800_53: AC-6

- [ ] **K8S-DKR-003** Check published ports, firewall rules and container connectivity  
  *Severity if fail:* Medium | *Type:* Config Review  
  *Objective:* Finds container ports open on all interfaces and containers that talk to each other with no limit.  
  *Steps:*
  1. List published ports for each container.
  2. Find ports bound to 0.0.0.0 that need only local access.
  3. Check the host firewall for rules that the container runtime bypasses.
  4. List the Docker networks and the containers on each.
  *Example:* `docker ps --format "{{.Names}} {{.Ports}}"; docker network ls; docker network inspect bridge; iptables -S DOCKER-USER`  
  *Expected:* Ports bind to 127.0.0.1 unless public use is needed. Containers share a user-defined network only when they must talk to each other.  
  *Refs:* k8s_top10: K05; cloud_native_top10: CNAS-6, CNAS-1; cheatsheet: Docker_Security_Cheat_Sheet; cwe: CWE-668, CWE-1327; attack: T1190; nist_800_53: SC-7, CM-7

- [ ] **K8S-DKR-004** Check resource limits and restart policy on containers  
  *Severity if fail:* Medium | *Type:* Config Review  
  *Objective:* Finds containers that can use all memory, CPU, processes or restarts on a host.  
  *Steps:*
  1. List memory, CPU, pids and ulimit settings of each container.
  2. Find containers with no limit.
  3. Check the restart policy and the maximum restart count.
  4. Run a stress test in a test container.
  *Example:* `docker inspect --format "{{.Name}} {{.HostConfig.Memory}} {{.HostConfig.CpuShares}} {{.HostConfig.PidsLimit}} {{.HostConfig.RestartPolicy}}" $(docker ps -q); docker stats --no-stream`  
  *Expected:* Each container has memory, CPU and process limits and a bounded restart policy. A stress test does not harm other containers.  
  *Refs:* k8s_top10: K01; cloud_native_top10: CNAS-9; cheatsheet: Docker_Security_Cheat_Sheet, Denial_of_Service_Cheat_Sheet; cwe: CWE-770; attack: T1499, T1496; nist_800_53: SC-5, SC-6

- [ ] **K8S-DKR-005** Check Docker secrets and build-time secret handling  
  *Severity if fail:* High | *Type:* Config Review  
  *Objective:* Finds secrets in image layers, build arguments and container environments.  
  *Steps:*
  1. Search Dockerfiles for ARG, ENV or COPY that handle credentials.
  2. Run docker history on each image.
  3. Check if builds use BuildKit secret mounts.
  4. Check that runtime secrets use Docker secrets or an external store.
  *Example:* `docker history --no-trunc <image>; grep -nE "ARG|ENV" Dockerfile | grep -iE "pass|token|key|secret"; docker build --secret id=mysecret,src=./secret.txt .`  
  *Expected:* Images hold no secrets in layers, ARG or ENV. Builds use secret mounts and runtime secrets come from a managed store.  
  *Refs:* k8s_top10: K03; cloud_native_top10: CNAS-5; cheatsheet: Docker_Security_Cheat_Sheet, Secrets_Management_Cheat_Sheet; cwe: CWE-798, CWE-312; attack: T1552.001; nist_800_53: IA-5, SC-28  
  *See:* CICD-CRED-005

- [ ] **K8S-DKR-006** Check the Docker daemon log level and host benchmark results  
  *Severity if fail:* Low | *Type:* Config Review  
  *Objective:* Finds Docker hosts with debug logging or other weak daemon settings.  
  *Steps:*
  1. Read the log-level setting in daemon.json and the dockerd command line.
  2. Run a Docker host benchmark tool.
  3. List failed checks.
  4. Fix or record each failed check.
  *Example:* `cat /etc/docker/daemon.json; ps aux | grep "[d]ockerd"; docker-bench-security`  
  *Expected:* The daemon log level is info unless debug is needed for a short time. Failed benchmark checks are fixed or recorded with an owner.  
  *Refs:* k8s_top10: K07; cloud_native_top10: CNAS-10, CNAS-1; cheatsheet: Docker_Security_Cheat_Sheet; cwe: CWE-1188; nist_800_53: AU-2, CM-6


## EXP

- [ ] **K8S-EXP-001** Check that the API server is not open to the Internet  
  *Severity if fail:* High | *Type:* Manual  
  *Objective:* Finds API servers that any host on the Internet can reach.  
  *Steps:*
  1. Find the public address of the API server from DNS, kubeconfig and cloud settings.
  2. Connect to port 6443 from an outside network.
  3. Read the authorized network list of the managed service.
  4. Make sure only trusted source ranges are allowed.
  *Example:* `nmap -p 6443 <api-host>; curl -k https://<api-host>:6443/version; aws eks describe-cluster --name <c> --query cluster.resourcesVpcConfig; az aks show -n <c> -g <rg> --query apiServerAccessProfile; gcloud container clusters describe <c> --format="value(masterAuthorizedNetworksConfig)"`  
  *Expected:* The API server is reachable only from trusted networks or a private endpoint. An outside host cannot connect to port 6443.  
  *Refs:* k8s_top10: K06; cloud_native_top10: CNAS-3; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-668, CWE-1327; attack: T1190, T1133; nist_800_53: SC-7, AC-17

- [ ] **K8S-EXP-002** Check version and certificate details that the API shows to outsiders  
  *Severity if fail:* Low | *Type:* Manual  
  *Objective:* Finds information leaks from the version endpoint and from certificate names.  
  *Steps:*
  1. Send an unauthenticated request to the /version path.
  2. Read the Subject Alternative Names of the API server certificate.
  3. Look for private addresses and internal host names in the SAN list.
  4. Check if the response gives the exact release.
  *Example:* `curl -k https://<api-host>:6443/version; openssl s_client -connect <api-host>:6443 </dev/null | openssl x509 -noout -ext subjectAltName`  
  *Expected:* The version path is not reachable from outside or needs authentication. The certificate shows no private addresses or internal names.  
  *Refs:* k8s_top10: K06; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-200; attack: T1190; nist_800_53: SC-7, CM-7

- [ ] **K8S-EXP-003** Check that kubelet and etcd ports are closed to untrusted hosts  
  *Severity if fail:* Critical | *Type:* Manual  
  *Objective:* Finds node and control plane ports that expose the kubelet, etcd or other components.  
  *Steps:*
  1. List the open ports on a control plane node and a worker node from a pod network host.
  2. Check ports 10250, 10255, 2379, 2380, 10257 and 10259.
  3. Check that only the API server can reach the kubelet and etcd.
  4. Compare the result with the firewall and security group rules.
  *Example:* `nmap -p 2379,2380,6443,10248-10260,30000-32767 <node-ip>; kubectl get nodes -o wide`  
  *Expected:* Only the API server and named hosts reach the kubelet and etcd ports. Read-only kubelet port 10255 is closed.  
  *Refs:* k8s_top10: K06, K07; cloud_native_top10: CNAS-6, CNAS-3; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-668, CWE-306; attack: T1190, T1046; nist_800_53: SC-7, CM-7

- [ ] **K8S-EXP-004** Check that etcd needs client certificates and is isolated  
  *Severity if fail:* Critical | *Type:* Config Review  
  *Objective:* Finds etcd servers that accept unauthenticated clients or serve other components.  
  *Steps:*
  1. Try to connect to etcd without a client certificate.
  2. Check the etcd peer and client TLS settings.
  3. Check that only API servers hold etcd client certificates.
  4. Check that no other component uses the main etcd keyspace.
  *Example:* `etcdctl --endpoints=https://<etcd>:2379 get / --prefix --keys-only; ps aux | grep etcd | tr " " "\n" | grep -E "client-cert-auth|peer-client-cert-auth"`  
  *Expected:* An etcd request with no valid client certificate fails. Only the API servers can connect, and etcd is behind a firewall.  
  *Refs:* k8s_top10: K06, K07; cloud_native_top10: CNAS-3; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-306, CWE-319; attack: T1190; nist_800_53: SC-7, IA-3

- [ ] **K8S-EXP-005** Find exposed dashboards and web UIs for cluster management  
  *Severity if fail:* High | *Type:* Manual  
  *Objective:* Finds management web interfaces that give cluster rights to outsiders or to anyone in the network.  
  *Steps:*
  1. List Services and Ingresses for dashboard, monitoring and admin tools.
  2. Open each address from an untrusted network.
  3. Check the rights of the service account of each tool.
  4. Check that an authenticating proxy sits in front.
  *Example:* `kubectl get svc,ingress -A | grep -iE "dashboard|admin|grafana|prometheus|argo"; kubectl get clusterrolebindings -o wide | grep -i dashboard`  
  *Expected:* No management interface is public without strong authentication. The service account of each tool has minimal rights.  
  *Refs:* k8s_top10: K06, K02; cloud_native_top10: CNAS-3; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-306, CWE-668; attack: T1190, T1133; nist_800_53: SC-7, AC-6

- [ ] **K8S-EXP-006** Check NodePort and LoadBalancer services for unwanted exposure  
  *Severity if fail:* Medium | *Type:* Config Review  
  *Objective:* Finds internal services that are public through NodePort or cloud load balancers.  
  *Steps:*
  1. List all Services of type NodePort and LoadBalancer.
  2. Check the source ranges and security groups of each.
  3. Check the nodes for services in the 30000-32767 range.
  4. Ask the owner to justify each public service.
  *Example:* `kubectl get svc -A -o wide | grep -E "NodePort|LoadBalancer"; nmap -p 30000-32767 <node-ip>`  
  *Expected:* Only reviewed services are public. Other services use ClusterIP, and each public service has restricted source ranges.  
  *Refs:* k8s_top10: K06; cloud_native_top10: CNAS-6; cheatsheet: Kubernetes_Security_Cheat_Sheet; cwe: CWE-668; attack: T1190; nist_800_53: SC-7


## DKR

- [ ] **K8S-DKR-007** Check that Node.js images hold only production dependencies and set NODE_ENV  
  *Severity if fail:* Low | *Type:* Config Review  
  *Objective:* Finds Node.js images with development packages and with non-production framework settings.  
  *Steps:*
  1. Read the Dockerfile of each Node.js image.
  2. Make sure the install step uses npm ci with the omit=dev option.
  3. Make sure the final image sets NODE_ENV to production.
  4. List the packages in the final image and look for development packages.
  *Example:* `grep -nE "npm (ci|install)|NODE_ENV" Dockerfile; docker run --rm IMAGE npm ls --omit=prod --depth=0`  
  *Expected:* The final image has no devDependencies. NODE_ENV is production.  
  *Refs:* cheatsheet: NodeJS_Docker_Cheat_Sheet, NPM_Security_Cheat_Sheet; cwe: CWE-1104

- [ ] **K8S-DKR-008** Check .dockerignore for secrets and local node_modules  
  *Severity if fail:* High | *Type:* Config Review  
  *Objective:* Finds Docker builds that copy credentials or modified local packages into the image.  
  *Steps:*
  1. Find the .dockerignore file next to each Dockerfile.
  2. Make sure it lists node_modules, .env files, credential files, .npmrc and logs.
  3. Build the image and list the files in the application folder.
  4. Make sure no ignored file is in the image.
  *Example:* `cat .dockerignore; docker build -t test . && docker run --rm test ls -la /usr/src/app`  
  *Expected:* The .dockerignore file excludes secrets and local dependencies. The built image holds none of them.  
  *Refs:* cheatsheet: NodeJS_Docker_Cheat_Sheet; cwe: CWE-538, CWE-200

- [ ] **K8S-DKR-009** Check signal handling and graceful shutdown of the container process  
  *Severity if fail:* Low | *Type:* Manual, Config Review  
  *Objective:* Finds containers where the application misses stop signals and ends in an abrupt kill.  
  *Steps:*
  1. Read the CMD instruction. Make sure it uses the exec form and starts node directly, not npm or a shell.
  2. Make sure an init process such as dumb-init runs as PID 1.
  3. Start a test container and send SIGTERM with docker kill.
  4. Start a slow request and send the signal. Make sure the application finishes it and closes connections before it ends.
  *Example:* `docker kill --signal=SIGTERM CONTAINER; curl -m 90 http://localhost:3000/slow`  
  *Expected:* The application receives SIGTERM and SIGINT, finishes active requests and then ends.  
  *Refs:* cheatsheet: NodeJS_Docker_Cheat_Sheet; cwe: CWE-404

- [ ] **K8S-CMP-007** Check file modes of control plane manifests and kubeconfig files  
  *Severity if fail:* High | *Type:* Config Review
